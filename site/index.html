Claude OKF Repo Kit

A spec-driven workflow for Claude Code: you provide the goal, Claude Code makes recorded decisions and iterates until the goal is met — with guardrails.

What it is

Repos driven by Claude Code lose their goal, contracts, and decisions between sessions. This kit installs a small, durable structure — built on the Open Knowledge Format — that makes the repo itself the memory:

FileWhat it holds
CLAUDE.mdThe objective, decision policy, guardrails, and workflow. Loaded every session; preloads the goal and knowledge indexes via imports.
docs/GOAL.mdThe goal: problem, target state, verifiable success criteria, and an ordered milestone backlog.
docs/specs/Behavior and contracts Claude Code must preserve.
docs/adr/Architecture decisions — including the ones Claude Code itself proposes.
docs/log.mdA dated changelog of what changed and why.
docs/okf-map.ymlWhich specs and ADRs govern which source areas.
.claude/hooks/Guardrail hooks that block ending a turn with code and docs out of sync.
scripts/okfA repo-local helper: stale-mapping checks, spec drafts, ADR suggestions.

How Claude Code works with your repo

This is the part that matters day to day: what actually happens when you open the repo and talk to Claude Code. Everything below is installed behavior, not aspiration — it is written into the kit's CLAUDE.md, which Claude Code loads at the start of every session.

Session start: context without re-reading the repo

Claude Code never holds your whole repo in its context window, and it doesn't need to. The installed CLAUDE.md imports three small files at load time — docs/GOAL.md and the spec and ADR indexes — so every session begins already knowing the goal, which milestones are done, and what knowledge exists. Full specs, ADRs, and code stay on disk until a task needs them; the indexes and the source-to-doc map tell Claude exactly which file to read for the task at hand. The conversation is a scratchpad; the docs bundle is the memory.

The first session: a goal interview, not a blank form

If the goal file still contains template placeholders, Claude Code doesn't start working — it interviews you first, a few questions at a time, and drafts the goal from your answers for your confirmation:

  1. What are you building, and for whom?
  2. What exists when it's done — concretely?
  3. How is that verified mechanically? What's the test command?
  4. What should this repo deliberately not do?
  5. Which stack and dependency choices are fixed, and which may Claude decide later through proposed ADRs?
  6. What's the first shippable slice, and how do we check it?

It pushes back on answers it can't verify — "migrate the API to GraphQL" is a direction, not a done state — and in an existing codebase it proposes answers from the code first and lets you correct them.

Saying "continue": the iteration loop

Once the goal exists, you don't have to write tasks. Ask Claude Code to continue and it runs the loop:

  1. Take the first unchecked milestone from docs/GOAL.md.
  2. Impact analysis — name the specs and ADRs that govern the files about to change, and read them.
  3. Implement the smallest change that satisfies the milestone.
  4. Run the test command and make it pass.
  5. Knowledge alignment — update the governing spec or ADR if behavior changed, and add a dated docs/log.md entry. The stale-map check catches anything missed.
  6. Check the milestone off only when its stated verification passes, then take the next one.

The loop stops on its own in exactly three cases: the backlog is empty, a decision reserved for you comes up, or you say stop. An empty backlog isn't a dead end — Claude reports the goal met, then proposes candidate next milestones (from the log's known items, ADR revisit triggers, and extensions inside your non-goals) and adds nothing until you choose.

How decisions get made

The division of labor is explicit: you own the goal; Claude Code drives the decisions that reach it — on the record.

  • Implementation choices inside existing specs, accepted ADRs, and the guardrails are Claude's to make without asking.
  • Decision-shaped changes — a new dependency, persistence model, auth approach, API contract, deployment shape — start with an ADR Claude writes itself, marked status: proposed, covering context, decision, alternatives, consequences, and a rollback trigger. It implements against the proposed ADR and flags it for you.
  • You review asynchronously: scan docs/adr/ for proposed entries and accept, request changes, or revert. Accepting means flipping the status to accepted — edit it yourself or tell Claude to; rejecting reverts the work per the ADR's rollback trigger. Accepted ADRs become binding constraints on all future sessions.
  • Reserved for you alone: changing the goal, superseding an accepted ADR, and every action the guardrails gate.

Guardrails, standing in every session

  • Tests run after every change; a milestone with failing tests is not done.
  • Failing tests are never deleted, skipped, or weakened to force a green run.
  • Secrets never enter tracked files; env and credential files are confirmed git-ignored before they're created.
  • Security-sensitive changes — auth, input parsing, crypto, network exposure, permissions — get an ADR check.
  • Force pushes, data deletion, publishing, deploying, and external calls with side effects wait for your explicit go-ahead, every time.
  • Outcomes are reported as they are: failures, partial progress, and skipped steps stay visible.

Know the limit: these guardrails are instructions, not mechanical enforcement. The kit's hooks enforce docs sync and nothing else. When a rule must be guaranteed rather than followed — tests green before merge, no secrets in commits — put it in your repo's own CI and branch protection, on top of this kit.

Interruptions cost minutes, not state

Sessions end: context windows fill, limits hit, laptops close. The loop is built for it. Milestone checkboxes, the dated log, ADRs, and git commits are the durable record — a fresh session reads them (the goal is preloaded) and knows exactly where the loop stands. If a session was cut off mid-milestone, the next one treats uncommitted changes as in-flight work: it reconciles them against the first unchecked milestone and the newest log entry, then finishes or backs them out before taking anything new.

Anatomy of a conversation

What this looks like in practice — the pattern an installed repo produces, request by request:

You ask for a capability: "make sure this repo supports X."

Claude reads the goal and the governing specs and ADRs first, reports the gap between what exists and what you asked for, then makes the smallest change that closes it. Behavior changes land together with their spec updates, an ADR if the change is decision-shaped, a log entry, and a full verification run — and the summary tells you what passed, what's proposed for your review, and what the change deliberately does not do.

You ask a question: "how does this part work?" or "is it worth adding Y?"

You get an assessment grounded in the repo's own files — including honest trade-offs and a recommendation — not an unrequested edit. If the answer suggests an improvement, Claude offers it and waits; work starts when you say yes.

You say "yes" or "continue."

Claude runs the loop: impact analysis, smallest change, tests, docs sync, verification, honest report. Decisions it had to make along the way are waiting for you as proposed ADRs, and the log tells the story in dated entries you can read months later.

The backlog runs out.

Claude reports the goal met and stops building. Instead of inventing scope, it lays out your options: known items from the log, revisit triggers from accepted ADRs, extensions that fit your non-goals — and, flagged separately, ideas that would need you to revise a non-goal first. You pick; it drafts the chosen milestones with verifications; the loop resumes.

You come back after a week.

Nothing is re-explained. The goal, milestone state, and knowledge indexes load automatically; the log and ADRs carry every decision since; "continue" means the same thing it meant last time.

Install

The kit is a reviewable source repo. Clone it, point the installer at your target repo, and it chooses the safe path — a fresh setup for new or empty repos, a non-destructive update (backups, merged settings, numbered candidates) for existing ones:

git clone https://github.com/lilabrooks/claude-okf-repo-kit.git
cd claude-okf-repo-kit
bash scripts/install-kit /path/to/target-repo
bash scripts/verify-install /path/to/target-repo

Then open the target repo in Claude Code — it runs the goal interview with you before the first task. Full instructions, manual paths, and verification details are in the README.
