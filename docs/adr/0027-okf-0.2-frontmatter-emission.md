# Status

Proposed (authored per the decision policy; awaiting owner review)

# Context

OKF 0.2 supersedes 0.1 with two breaking changes (SPEC.md §13.1): `timestamp`
is superseded by `generated.at`, and the body `# Citations` list is superseded
by the `sources` frontmatter family. Everything else carries forward unchanged.

The kit is on the wrong side of both halves of this, in a way that a repo's own
migration cannot fix:

- `scripts/okf` writes `timestamp:` into every document it scaffolds, at three
  sites — `draft`, `new-adr`, and `new-spec`. This ADR file was itself
  scaffolded with `timestamp:` while being written to remove it.
- `templates/CLAUDE.md` and `templates/AGENTS.md` document `okf_version: "0.1"`
  and describe frontmatter as "OKF v0.1", and all three templates carry
  `timestamp:` in their own frontmatter.
- `scripts/update-existing-repo` hardcodes `okf_version: "0.1"` when it writes a
  bundle root for a repo that has none.

The consequence is compounding: a repo installed today is stamped 0.1 and fires
an OKF drift note on its first session, and a repo that has already migrated to
0.2 regresses the moment anyone runs `okf new-adr`. spec-drift migrated its
bundle to 0.2 on 2026-07-25 and would have regressed on its next scaffolded
document.

`generated.by` is REQUIRED within `generated` (§5.2), so emitting the field at
all forces a choice of actor under the §7 convention.

# Decision

- The three `scripts/okf` scaffold sites emit
  `generated: { by: process:okf-scaffold, at: <ISO 8601 UTC> }` in place of
  `timestamp: <ISO 8601 UTC>`. The instant recorded is unchanged; only the field
  shape moves. The flow-mapping form is used because it is what SPEC.md §5.2
  shows, and it keeps the emitted frontmatter to one line per key.
- The actor is `process:okf-scaffold`, the §7 `process:<id>` form. A scaffold
  skeleton is machine-produced, which is what the field records. Whoever fills
  the document in may overwrite `by` with their own actor; the kit does not
  require it, because a stale `by` on a filled document is a smaller defect than
  a fabricated one.
- `templates/CLAUDE.md` and `templates/AGENTS.md` declare `okf_version: "0.2"`,
  describe frontmatter as OKF v0.2, and keep the version-policy section's worked
  example current. All three templates carry `generated` in their own
  frontmatter instead of `timestamp`.
- `scripts/update-existing-repo` writes `okf_version: "0.2"` into a bundle root
  it creates.
- This is an installed-behavior change, so `VERSION` bumps (ADR 0010) and
  `site/` is reviewed for accuracy (ADR 0016).

Not in scope: the `# Citations` → `sources` half of §13.1 (the kit's
scaffolders never emitted a `# Citations` body list, so there is nothing to
migrate), the additive 0.2 families (`sources`, `verified`, `stale_after`,
`Attested Computation`), and the kit's own `docs/` bundle, which is source-only
and migrates separately without a `VERSION` bump.

# Alternatives considered

- **Drop `timestamp` and emit nothing.** OKF 0.2 makes the whole `generated`
  family optional and §11 forbids consumers rejecting a document for missing it,
  so this would conform. Rejected: it silently discards the creation instant the
  scaffolders have always recorded, which is a real loss of provenance for a
  one-key saving.
- **`by: okf/<kit_version>`, the §7 `<producer>/<version>` tool form.** More
  precise about which kit produced the skeleton. Rejected: `VERSION` is
  source-only and never installed (ADR 0010), so the helper would have to parse
  `kit_version` out of the stamp file — which brownfield repos are explicitly
  allowed not to have (ADR 0018). That trades a correct-but-vague actor for one
  that is sometimes absent.
- **`by: human:<owner>`.** Rejected: §7 requires the `human:` prefix for
  hand-authored or human-confirmed content specifically because consumers derive
  trust tiers from it (§5.3). A scaffold skeleton is neither, and claiming it
  would inflate every generated draft to human-reviewed.
- **Emit `verified` alongside `generated`.** Rejected: `verified` records a
  confirmation event that has not happened at scaffold time. Asserting one would
  be fabricating provenance.
- **Leave the scaffolders on `timestamp` and let each repo fix its own.**
  Rejected: it is the defect that cannot be fixed downstream. Every install
  regresses on its next scaffolded document, forever.

# Consequences

- Repos installed from this kit version are born conformant with the current
  spec, and the SessionStart OKF drift note stops firing on fresh installs.
- Documents scaffolded into an already-migrated repo no longer drag it back to
  v0.1 field names.
- Downstream repos already carrying `timestamp:` are not touched. Nothing in the
  kit rewrites existing documents, and §13.1 lets consumers fall back to a legacy
  `timestamp` when `generated` is absent, so mixed bundles stay readable. Repos
  migrate on their own schedule under the OKF version policy.
- `docs/specs/okf-helper-command.md`, `docs/specs/repo-kit-packaging.md`, and
  `docs/specs/installer-scripts.md` must describe the emitted frontmatter as
  `generated`, and stay in sync with the three scaffold sites.
- The kit's own `docs/` bundle is now internally inconsistent: 34 files still
  carry `timestamp:` and `docs/index.md` still declares `okf_version: "0.1"`
  while the kit ships 0.2 emission. That is deliberate sequencing, not an
  oversight — it is source-only, affects no install, and is tracked as follow-up
  work in `docs/log.md`.

# Rollback / revisit trigger

- **Revisit** if OKF 0.3 changes the provenance families again, or if the actor
  convention gains a form that fits a scaffolder better than `process:<id>`.
- **Revisit** if filled documents are observed carrying `by:
  process:okf-scaffold` long after an agent rewrote their content, and the stale
  actor starts misleading a consumer that derives trust tiers. The fix would be
  to require the filling agent to overwrite `by`, which this ADR deliberately
  leaves optional.
- **Rollback** is three `printf`/heredoc lines in `scripts/okf`, the template
  and installer strings, and a `VERSION` revert; no data migration is involved,
  because nothing rewrites existing documents.
